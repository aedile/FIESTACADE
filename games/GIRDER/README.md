# GIRDER

**Nintendo's 1981 Donkey Kong, emulated on an ESP32-C6 Fiesta medal.** A Z80 for
the game and an 8035 microcontroller for the sound — playing the real music,
from the real program, through the real DAC.

A San Antonio Fiesta medal is a collectible pin. This one plays Donkey Kong.

---

## 🎮 Quick Start Guide

### How to Play

You hold the medal upright, like a phone. Donkey Kong's monitor was already
vertical, so the picture stands up the same way you do.

| Control | What it does |
|---|---|
| **Tilt left / right** | Run |
| **Tilt away / toward you** | Climb up and down |
| **Middle button** | Jump |
| **Power button, short press** | Insert a coin and start |
| **Power button, hold 1 second** | Power off |

Only the axis you have tilted further counts, matching the four-way gate on the
cabinet's stick.

Tilt is measured against however you are holding it right now. Coin up to
re-centre — worth doing before your first climb, since the neutral pose is
captured at boot while the medal is probably lying on a desk.

### Charging

USB-C. Holding the power button for a second cuts the battery rail.

### Troubleshooting

**Mario runs the wrong way.** Each axis is one sign in `main/input.cpp`
(`X_SIGN`, `Y_SIGN`).

## 🔨 Building Your Own

```sh
git clone https://github.com/aedile/GIRDER.git
cd GIRDER
python3 tools/convert_roms.py /path/to/dkong
docker run --rm -v "$PWD":/project -w /project espressif/idf:v5.3.4 \
    idf.py -B build_docker build
cd build_docker && esptool --chip esp32c6 -p /dev/cu.usbmodemXXXX \
    -b 460800 write_flash @flash_args
```

Flashing has to run **from inside `build_docker`** and **from the host** —
Docker Desktop on macOS cannot reach USB.

### The ROMs

Not included. You need MAME's `dkong` set — the TKG-04 upgrade. The converter
checks every CRC and mirrors the 2 KB sound ROM to fill the 8035's 4 KB address
space, exactly as the board's address decoding does.

## 🔬 Technical Details

### The original hardware

A Z80 at 3.072 MHz, an **8035 microcontroller** for the sound, and an 8257 DMA
controller that copies the sprite list into the sprite RAM once a frame when the
game writes to 0x7D85.

### The sound is a program, not a synthesiser

This is the part worth doing properly. Donkey Kong's music and most of its
effects are not generated by a sound chip — there isn't one. The 8035 plays them
by writing eight-bit samples to a DAC on its port 1, fetching sample data a page
at a time through its BUS port with the page number in the low bits of port 2.

So `core/mcs48.h` is an interpreter for that MCU, written for this project, and
what comes out of the speaker is the real program's own output rather than an
imitation of it. Only a handful of percussive effects — the footsteps, the jump,
the stomp — are discrete circuits on the board, and those are synthesised.

One detail that matters: **the DAC is unipolar.** The program swings it inside
whatever range it likes and the board's coupling capacitor throws the offset
away. Assuming it sits at mid-scale gives you a large DC offset and a signal
that never crosses zero, so there is a one-pole high pass here doing what the
capacitor does.

### The character colours come from a PROM, not from memory

Nothing the CPU writes chooses a character's colour. A PROM is indexed by the
tile's column and by which band of four rows it sits in, so the girders, the
ladders and the score line get their colours from *where they are on the screen*.
The CPU only ever picks the character.

Both palette PROMs drive inverters, so the resistor weights are subtracted from
full brightness rather than added to black, and wherever the low two bits of a
palette entry are clear the output is tri-stated to real black.

### The DMA

The 8257 has two channels and a latch between them. One channel reads memory
into the latch and the other writes it back out somewhere else, which together
make a memory-to-memory copy. That is how the sprite list gets from work RAM
into the sprite RAM, and it happens the instant the game pokes 0x7D85.

## 📁 Project Structure

```
core/           platform-independent emulation, shared with the host harness
  dkong.c         Z80, memory map, the 8257 DMA, interrupt timing
  dkong_video.c   character map, sprites, the inverted palette PROMs
  dkong_sound.c   the 8035 sound board and the discrete effects
  mcs48.h         an Intel MCS-48 (8035) interpreter
  z80/            Marat Fayzullin's Z80 (non-commercial — see notices)
main/           the ESP32 application
components/     display, IMU and audio HAL for the Waveshare board
host/           builds the same core on a desktop; frames to PPM, audio to WAV
tools/          ROM converter
```

## 💻 Running It on Your Computer

```sh
cd host && make
./harness /tmp/out 30 --every 4 --wav /tmp/dk.wav \
    --script "12.0:coin=1,13.0:coin=0,15.0:start=1,16.0:start=0,20.0:right=1,23.0:jump=1"
```

The harness writes the **native** 256×224 frame, which is the picture lying on
its side. Turn it 90° clockwise to look at it the right way up.

## 📌 Status and Known Gaps

The game runs at full speed — 60.6 Hz, correct timing — with sound.

- **The panel refreshes at about 50 of those frames.** The game logic and its
  timing are correct.
- Sprites are drawn a whole frame at a time. The real board buffers one
  scanline and can only show 16 sprites on any given line; a display list that
  exceeded that would look different here.
- The discrete effects are reconstructions, tuned by ear rather than modelled.
- Cocktail flip-screen is read from the latch but not applied.
